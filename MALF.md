# malf

Unified build system for coderoast C++ projects. Replaces per-repo `dev.sh` scripts with a single portable tool.

`malf` is a local build helper — not the source of cross-repo package pins, release sequencing, or compatibility policy. Those live with the consuming projects.

## Installation

Add `malf/` to your PATH, or symlink the script:

```sh
ln -sf /path/to/coderoast/malf/malf ~/.local/bin/malf
```

## Usage

Run `malf` from any directory that contains a `conanfile.py`, or from any parent of dirs that contain one (a repo root, the workspace root).

```
malf build   [target] [--asan|--profile <name>]
malf test    [target] [--asan|--profile <name>] [--verbose] [--filter REGEX]
malf lint    [--all-files] [-c|--console]
malf format  [--check]
malf commands
malf compile-commands
malf bench   [target] [--quick] [--filter REGEX] [--compare] [--repetitions N] [--threshold F] [--asan|--profile <name>]
malf clean   <build|conan|editables|stale|all>   # no default; `all` is the nuclear form
malf run     <exe-name> [args...]
malf slot    [status|acquire|release]
```

### Verbs — one compile surface

`build` compiles **everything** for the target: the package, its tests, and its
benches. `test` and `bench` run (`ctest` / the benchmark executables) on top of
the **same incremental build** — the verbs differ only in what they run, never
in what they compile, so a test- or bench-only TU can't rot unseen and first
fail in the release pipeline (the 1.7.2 drift-at-tag class).

### Targets — packages under the invocation point

**The rule is invocation-point INDEPENDENCE: `malf <verb> <dir>` is exactly
`cd <dir> && malf <verb>`.** How the path is spelled never changes what gets built.

* Any resolved dir → **every package under it, dependency-ordered**: a
  multi-package repo root sweeps the whole repo, the workspace root sweeps the
  whole workspace, a mono-package root or a leaf subfolder degenerates to the
  single package. Each member runs as its own `malf <verb> <pkg>` process — the
  exact `&&`-chain semantics, first failure stops the sweep.
* `--only` → exactly the recipe **at** the resolved dir and nothing below it.
  It refuses (exit 1) when that dir carries no `conanfile.py`, rather than
  quietly sweeping instead.

> **Until 2026-09-04 an explicit arg naming a package dir meant "that package
> only", and it was a defect.** It made the two spellings of one intent disagree
> in exactly the two repos that then had a root recipe *and* sub-recipes —
> `insight-eidos` (5) and `coderoast-ipc` (4): `malf build insight-eidos` built
> ONE package while `cd insight-eidos && malf build` built five. **It failed
> silently** — the short build exits 0, so the operator reads a green over a
> surface that was never compiled. Measured during the `N135` suite rename: a
> `ctest -N` check reported the OLD suite names as still live, because
> `malf build insight-eidos` had left `insight-eidos/sift` at the previous day's
> binary. The rename looked incomplete; the build was. Rebuilding one package is
> still a real need — eidos's root recipe is a three-module compile target, not an
> umbrella — so it survives as `--only`, a stated intent rather than an accident
> of typing.
* Content-only packages (a `conanfile.py` but no `CMakeLists.txt` — umbrella
  metapackages, scenario corpora) are skipped with a note.

### Build trees — package-anchored

Every build tree lives at `<pkg>/build-<profile-key>` (`build-clang21-libcxx-release/`
(the dev default), `build-gcc16-release/`, `build-clang21-asan/`, …) — anchored at
the **package**, never the invocation CWD, and always profile-named. The target
build, the editable-dep build, and a subfolder invocation all share **one tree per
(package, profile)**: a bare `build/` is never created, an ASan tree can never
clobber a release one, and the old "cd into a package subdir → second,
inconsistent build tree that links a stale dependency" footgun is structurally
gone. The merged clangd DB lands at the repo root's default-leg tree
(`<repo>/build-clang21-libcxx-release/compile_commands.json` — what `.clangd` reads).

The key is `(package, profile)` and has **no dimension for role**, deliberately — see
*Compile commands* below for what that costs the editor index, why the tree is not split by
role, and the rule that replaces splitting it (**the richer role wins the tree**).

The role switch also costs **ninja dependency records**, and that cost is paid by every build
rather than the index: a recompaction of `.ninja_deps` while a tree is in the dependency role
drops the record of every test and bench object, the objects stay on disk, and in a C++ module
tree ninja can then link such an object stale while every test passes (measured 2026-10-06:
`malf test insight-metalog` 357/357 over a header edit it never compiled). So before every
`cmake --build` — a package's and an inventory cell's — `ninja_deps_guard.py` deletes each
existing output its tree's own ninja holds no record for, naming them, and refuses the build if
the records cannot be read. A deleted output is dirty on every path through ninja, so the build
that follows recompiles it.

### Commands

| Command | Description |
|---|---|
| `build` | bootstrap local workspace package deps, `conan install`, configure, then compile package + tests + benches into `<pkg>/build-<key>/`. **The `-j` width is derived from both operands, the cores and the memory**: `max(1, min(cores, floor((memory − reserve) / cap)))`. The cores are the process's affinity (`nproc`), which a seat's cpuset partition narrows. The memory is the SEAT's, read when the build starts (`DN-119.D9` (1)): the least of `MemAvailable` minus every OTHER seat's unmet guarantee (Σ `max(0, memory.min − memory.current)` over the `seat_*.slice` cgroups) and, over this process's cgroup and every ancestor with a finite `memory.max`, `memory.max −` held, held being what the kernel cannot reclaim before it OOM-kills, read from `memory.stat` (anon, shmem, file_mapped, dirty and writeback pages, the unreclaimable kernel memory; page cache and reclaimable slab count as available, a cgroup with no `memory.stat` holds all of `memory.current`) — never `MemTotal`, so a build that starts beside another one gets what is left rather than its full width a second time, and a build inside a capped seat plans on its cap, not on the VM. The line carrying the four operands, the width and both memory terms is printed before the compile. The operands are measurements, in KiB: `MALF_BUILD_JOB_MEM_KB` (1.2 GiB a job), `MALF_SANITIZER_JOB_MEM_KB` (3 GiB a job under a sanitizer) and `MALF_FANOUT_RESERVE_KB` (2 GiB). A build whose largest process peaked above its cap prints a note naming both figures — never a failure: a width changes scheduling, never a verdict. Where neither `MemAvailable` nor a finite cgroup `memory.max` is reported the width is the cores alone, and the line says so. **Every conan act malf runs that may compile takes the same width** as `tools.build:jobs` — a `--build=missing` install, `store-create`'s third-party install, create and build, an inventory cell (conan's and cmake's), `commands`' test_package install — read when the act starts and printed under the act's name: unset, conan compiles at Python's `os.cpu_count()`, the machine's 16 whatever the seat (step 0 run 39903608377 was OOM-killed in the release seat with 16 `cc1plus`). **Inside the build environment the width reads the host's cgroup tree**: every act container shares the host's cgroup namespace, so the seat's `memory.max` binds there as on the host |
| `test` | same build flow, then `ctest`, its results written as JUnit to `<build dir>/malf-test.junit.xml`; a package declaring `backends:` in its working-tree packages.yml runs that ctest beside them (`environment with-backends <source dir>`, DN-142.D30 (5) E2b; inside the build environment the launcher already started them on the act's network, and the verb runs bare), each published on `127.0.0.1` and handed in `CODEROAST_BACKEND_<NAME>`, removed after; a green run is then judged for skips (`malf_recipe_tests.py judge-skips`, the source tree read off the build tree by `tree-source`): an undeclared skipped or disabled row fails it (DN-142.D23, below) |
| `bench` | same build flow, then run benchmark executables, output JSON to `bench_results/`. A run updates `baseline.json` **only when it is a baseline measurement**: unfiltered, not `--quick`, not `--compare`, and more than one repetition. Anything else prints, by name, which condition refused and how to make a baseline (`malf bench <pkg> --repetitions 5`), and leaves the file untouched — because a baseline replaced by a partial or low-precision run makes the NEXT comparison read noise as a regression or a win, with nothing in its output saying the baseline was the unusual half |
| `bench --compare` | variance-aware regression gate vs `baseline.json` (`bench_compare.py`): runs 5 repetitions by default, compares MEDIANS, and widens the `--threshold` floor (default ±10%) to 3×cv per bench — so honestly-noisy benches (the ±40–90pt pipeline swings) no longer false-positive while tight benches keep the floor |
| `lint` | clang-tidy on git-changed files (or `--all-files`). **Every finding fails the run**, a warning as much as an error — clang-tidy itself exits 0 on any check outside `WarningsAsErrors`, and a gate reading the exit code used to pass them. Requires a compile database — it refuses to run without one, because a flag-less clang-tidy reports phantom errors it cannot be right about. Under `--all-files` an empty file set is a scoping failure, not a pass. A TU clang-tidy **dies** on is reported as **NOT LINTED** by name, apart from the findings, and fails the run: a crash dump carries real paths and real line numbers, so merged into the findings it reads as a source defect while the file's zero coverage leaves no trace. It also DE-SYSTEMS first-party include roots before handing the database to clang-tidy: CMake marks an IMPORTED target's include directories SYSTEM, so our own editable packages arrive as `-isystem` and the checker reports nothing about them; the run rewrites those to `-I` in a derived database and prints what it rewrote and what it left. Third-party stays `-isystem`. **Every run ends with a one-line `SUMMARY`** naming the selection mode (`git diff --name-only HEAD` vs `--all-files`), the directory, the population the mode selected split into translation units and headers (`selected N = T translation unit(s) + H header(s)`: a header never reaches clang-tidy by itself, it is linted only through a TU that includes it, so the coverage question is `T` against `checked`), how many of those actually reached clang-tidy, and the finding / not-linted counts — because a green that does not state its scope reads the same whether it checked 400 files or none. A run that selected **zero** files says `CHECKED 0 — NOTHING WAS INSPECTED` and states in words that it is not a clean verdict. **Every translation unit leaves what it cost** (`tu_cost.py`, which also holds the per-TU time cap): its progress line carries `<elapsed> s  rss <max RSS> MiB  vm <peak address space> MiB`, and a `COST` line after the `SUMMARY` names the heaviest translation unit by each memory figure and the longest — the address space is the figure the child's cap bounds (a `ulimit -v`), and the width of the fan-out is derived from these measurements. **The width is derived like the build's**, by the same function and from the same seat-aware memory operand, `max(1, min(cores, floor((memory − reserve) / cap)))`, and its derivation is printed (`malf lint: -jN = …`); the cap is `MALF_LINT_MEM_LIMIT_KB` (1.75 GiB a child: the heaviest of 352 measured translation units peaked at 1 376 MiB of address space) and it is ENFORCED — each clang-tidy runs under `ulimit -v` at that figure, so no child takes more than the width counted it for. A unit that dies with its address space at the cap is reported `AT THE MEMORY CAP`, a third cause beside a checker death and a timeout, with its own remedy: raise the cap, and the width narrows with it. `format` keeps its own cap, `MALF_SOURCE_MEM_LIMIT_KB`. Under `--all-files` a TU with no compile command is a fatal coverage hole **unless the build gates it off this platform**: `platform_gate.py` finds every CMake line of the repo naming the file and, when each one sits in an `if()` branch built only of platform words (`WIN32`, `UNIX`, `APPLE`, `LINUX`, their `CMAKE_HOST_` forms, `NOT`/`AND`/`OR`) that `cmake -P` does not take on this host, the TU is **REFUSED** — named with the CMake line and branch, counted as `platform-refused` in the `SUMMARY`, and not fatal. A file no CMake line names, one under a project option, or one under a branch that IS taken here stays fatal; the verdict never reads a file name |
| `format` | clang-format all C++ files in-place (`--check` = `--dry-run --Werror`, non-zero on any violation). Resolves the style explicitly and refuses to run if it cannot, rather than let clang-format fall back to LLVM style unannounced. **Every run ends with a one-line `SUMMARY`** in the same vocabulary as `lint`'s, naming what the run did and where its population came from (`check`/`write` × `sweep`/`paths`), the directory, `selected` (every file the walk matched), `checked` (those handed to clang-format), the misformatted count in check mode, and `skipped` (the `MALF_SOURCE_MAX_FILE_KB` overruns) — so `selected = checked + skipped` is an identity on the line itself and a non-zero `skipped` is a visible coverage gap. A run that selected **zero** files says `CHECKED 0 — NOTHING WAS INSPECTED` and states in words that it is not a clean verdict, replacing `nothing to do`, which read as a pass. `misformatted` counts FILES, not diagnostics; the write mode reports no such count, because `clang-format -i` never says what it changed. The exit status is `xargs`'s 123 on any failing batch, so it is printed beside the count: rc non-zero with **zero** violations means clang-format failed for a reason that is not formatting, and those files were not checked at all. **Then a second phase, over the SAME population: the Code & Comment as Contract grammar** (`comment_contract_lint.py`, `ADR-26.D7`) — every `//` line in every C++ repo begins with one of `pre:` `post:` `invariant:` `assert:` `note:` `refs:` on its own line (a contract form may carry ONE untagged continuation line; a note and a refs never), the only multi-line comment is the framed `D-LSRC-n` law block, and the tool forms a machine reads (`} // namespace x`, `/*name=*/`, own-line `NOLINT…` preceded by its `note:`/`refs:`, `clang-format off/on`) are admitted. It reads the **post-format** text — in check mode it formats each file itself, its bytes on stdin with `--assume-filename=<the file>` so the style resolves upward from the file's own path, through `judge_text`, the one judging path `./pharos judge-comments` also calls — because the reflow swallows a `post:` tag into an overlong `pre:` line (measured 2026-09-05, clang-format 21.1.8) and a pre-format read cannot see it. The phase reds in every repo with no declaration (since `OPS-8.S13`, 2026-09-09 — the per-repo `comment_contract` key that made an unmigrated repo report-only was ripped when the last migration closed); every violation is printed with its site and, on the next line, `  fix: ` and its class's one fix text (`REMEDY`, keyed on every violation class — the same text Pharos's `cpp_format` findings and `./pharos judge-comments` print), and the `CCC SUMMARY` line carries files checked, comment lines and the by-form counts so a zero is distinguishable from nothing inspected. `refs:` addresses are checked for **form** here and for **resolution** by `scripts/registry_grammar_lint.py`, never both in one place. **One code rule rides the same phase, class `self-compare` (`RUL-206`)**: an `EXPECT_`/`ASSERT_` `EQ`/`LE`/`GE`/`STREQ` whose two top-level operands are identical once whitespace outside literals is removed and carry no call (`(` in code) cannot fail and reds; a call on both sides is never judged (`hash(seed)` twice is a determinism assertion), and the rule is blind to an operand compared with what it was computed from |
| `contract-gen` | `malf contract-gen [DIR|FILE...] [--out PATH]` renders the DERIVED contract surface (ADR-26.O3) from the tagged comment lines and law blocks the format gate counts: per declaration every tagged line it carries (`pre`/`post`/`invariant`/`assert`/`note`) and its `refs:`, a `TEST` under its name, every law block in full, the refs index and the `TEST` → `refs:` table. Stdout by default; `--out` writes a scratch file; `--declarations-only` is the narrower shape. Never committed — regenerate it. `--selftest` proves the renderer on a fixture. |

| `slot` | the **workspace build slot** — the coarse claim that one *lane* builds at a time across every repo, distinct from the per-build-directory lock `build`/`test` take for themselves. Its stamp carries two independent proofs, because a holder poses two different questions: an **anchor** (the holder's session pid plus that pid's start time, field 22 of `/proc/<pid>/stat` — never the mtime of its `/proc` directory, which is when the kernel instantiated the entry and can change under a live process) answers *is the holder still alive?*, and a 32-hex **token** answers *am I the holder?*. The anchor is the lane's SESSION and never an individual run — a per-run pid is gone between runs by design, so its death proves nothing, which is exactly why the hand-rolled `holder`-file protocol it replaces could not tell a corpse from a lane that was thinking. `acquire` claims a free slot, refuses a live one by name with a `REFUSED` line and **no token** (a token beside an acquire reads as its grant; the holder's token is shown only by `status`), and reclaims a provably dead one automatically. `release` needs `--token`; `--force` covers only a slot with no readable stamp, and a **live** holder cannot be forced at all — kill its anchor pid and the slot frees itself. A directory carrying no stamp `malf` wrote is `UNKNOWN`: never reclaimed for you, always shown to you. `status` prints `FREE` / `HELD` / `STALE` / `UNKNOWN` and exits `0` / `1` / `2` / `3`. **One slot per SEAT** (`DN-119.D9` (3)): the default path is the account's own state, `${XDG_STATE_HOME:-$HOME/.local/state}/coderoast-build/slot`, every directory created on the way mode 0700 — seat and account are one-to-one and the seats share no build state, so no account can open, or stall, another seat's slot. `MALF_BUILD_SLOT_DIR` overrides it (a runner's `.env` names it). `status` and `acquire` print the seat as the kernel reports it: the top-level cgroup, its `cpuset.cpus.effective` and `cpuset.cpus.partition`, and its `memory.max`, `memory.min` and `memory.swap.max`, each `absent` where the file is not there |

### Workspace bootstrap

`build`, `test`, and `bench` automatically register the target's sibling workspace packages as Conan editables and build them in dependency order into their own package-anchored trees. The set is the **build closure**, not the link closure: the target's transitive workspace `requires`, plus the workspace `test_requires` of *every member in the closure* — each dependency is configured as the top-level project of its own CMake preset, so its `PROJECT_IS_TOP_LEVEL` test and bench subtrees are ON and its own `test_requires` must resolve as well. Override the scan root with `MALF_WORKSPACE_ROOT` or disable it with `MALF_AUTO_WORKSPACE_DEPS=0`. (The recipe-graph queries live in `malf_graph.py` — one AST parser for deps / whole-workspace / member enumeration, and `steps`, the members with their first-party edges, the walk `store-create` runs.)

Example (`~/.bashrc`):
```sh
export MALF_WORKSPACE_ROOT="$HOME/workspace/coderoast"
```

### Compile commands

`build`, `test`, and `bench` configure with `CMAKE_EXPORT_COMPILE_COMMANDS=ON`, so each package build tree gets its own `compile_commands.json` automatically — and every build folds it into the repo root's merged default-leg DB (`<repo>/build-clang21-libcxx-release/compile_commands.json`, what `.clangd` reads), wherever the build was invoked from.

**A sweep settles the database whole.** When `build`/`test`/`bench` sweep several members, each member's dependency bootstrap re-configures the earlier members it requires with tests OFF — and where a repo has a root recipe (`insight-eidos`, `coderoast-ipc`) that root package's tree **is** the repo database's address, so each re-configure overwrote the file. Measured on `insight-eidos` 2026-09-21: the CI invocation (`malf build --profile linux-clang21-libcxx-release`) left **84 entries covering 79 of 244 tracked TUs**. So after the last member a sweep re-configures (and builds) every member left in dependency role, plus the repo-root member unconditionally, reads each role back from its `CMakeCache.txt` (still dependency → exit 1), and **recomposes** each repo database from the member trees — never accumulated, so an entry for a deleted TU does not survive a sweep that covers the repo. After it: **243 entries covering 241 of 244**, the 3 absent being the two platform-gated TUs below and `test_package/test_package.cpp`, which only `commands` configures. A single-package build (`--only`, or a leaf) still merges incrementally, and a dependency rebuild of a root recipe from another repo still truncates that repo's database until its next sweep — `lint --all-files` names that as a coverage hole.

Use `commands` or `compile-commands` only when you want that merged DB rebuilt from scratch, for example:
- you want `test_package` entries merged in for IDE navigation
- the merged DB carries stale entries from deleted/renamed packages

**One package, two roles, one tree.** In a single `commands` pass a package can be configured twice: once as the indexed **target** (tests and benches ON) and once as a sibling member's **dependency** (both OFF). Both writes land in the same `<pkg>/build-<key>` tree, because the build-tree key is `(package, profile)` and has **no dimension for role** — and the second write wins, so the merge would read a database with the target's test and bench TUs already removed. Measured 2026-09-03 at `clang21-libcxx-release`: `coderoast-ipc` produced **15 entries where the complete database is 19** (4 first-party TUs lost, 0 external) and `insight-canon` **60 where the complete database is 123** (63 first-party TUs lost, 0 external) — every one of the 67 a test or bench TU, both runs exiting 0.

The key does **not** gain a role dimension: the recipes bind a consumer to its dependency's build directory *by name*, so a second role-keyed tree would be the one consumers link while the other is the one `malf test` greens, and clangd reads one database anyway, so the role choice would only move. Instead the **richer role wins the tree** — the dependency configuration is a strict subset of the target one (verified: the two `CMakeCache.txt` differ only in the two feature variables and in `CMAKE_CTEST_COMMAND-ADVANCED`, which `enable_testing()` derives). So `commands` re-asserts the target role on every member a dependency bootstrap demoted, *before* the merge, and then reads each tree's own `CMakeCache.txt` back: a member still in dependency role, or one with no cache at all, exits **1** and names the variable and the file. The reasoning, the measurements and the rejected alternatives are in `malf` above `cmd_compile_commands`.

**A buildless member still has its `test_package` indexed.** A header-library recipe (`coderoast-server/server-logging`) declares no CMake generators, so its `conan install` writes no `CMakePresets.json` and its own preset configures nothing — but its `test_package` needs no preset at all: `commands` installs a synthetic conan consumer for it and runs `cmake -S <member>/test_package` against the toolchain that install wrote. Until 2026-09-03 the member loop `continue`d on the missing preset and skipped that configure too, so `coderoast-server` reported `test_package 4 present = 3 configured + 0 failed + 1 unreached` and **392 entries of which zero were `server-logging`'s** — the one translation unit proving that header-only logging seat's contract had never been in any editor index. The predicate is the **preset**, read off the build dir, never the absence of a `CMakeLists.txt`: a member that *does* declare a CMake project and produced no preset had a failed install and is fatal, which reading the source file could not tell apart. Both summary residuals — `unaccounted` members and `unreached` `test_package`s — are set differences against a census taken before the loop's first gate, so a future early exit is caught by arithmetic it cannot opt out of and the member is named.

### Path-independent package bytes

`global.conf` attaches `cmake/malf-path-map.cmake` to every conan CMake build (`tools.cmake.cmaketoolchain:user_toolchain`), staged beside `global.conf` in each conan home by malf and by every CI action that stages `global.conf`. It maps the source and build directories out of `__FILE__` and `std::source_location` through the language flags, so a package's bytes do not depend on its conan home or build folder; its header says why it is neither a profile flag nor a directory compile option.

`global.conf` names `malf_recipe_exports.py` (`user.malf:recipe_exports`), staged beside it in each conan home by malf and by every CI action that stages `global.conf`. Every first-party recipe keeps its `exports_sources` as the declared allowlist and calls the helper from `export_sources()`, which removes from the export every file git does not track: the export is the tracked files under the declared roots, so a recipe revision is a function of the commit, not of the desk. Outside a git checkout the export keeps its globs and warns; a home without the helper fails the export.

`global.conf` names `malf_recipe_tests.py` (`user.malf:recipe_tests`), staged the same way, and a results directory (`user.malf:test_results`, default `<conan home>/malf-test-results`). The helper holds the ONE test selection (DN-142.D5): `-LE corpus` for the default population, `-L corpus` for `--corpus`, and the zero-population guard (`ctest <selection> -N`, then `--no-tests=error`) for a run that owes a test. `malf test` reads its ctest arguments from it, and every first-party recipe calls `run_tests(self)` from `build()` after `cmake.build()`: a `conan create` runs the same selection over its build folder, writes `<name>/<package id>.xml` (JUnit) into the results directory (keyed by package id: a create also builds the upstream variants its graph lacks, and each runs its own tests), and fails on any red or on an enabled-testing tree that selects nothing. Beside it the default run writes `<package id>.corpus-listed.json` (every `corpus`-labelled name, listed and never run). When `user.malf:corpus_gates` names a document holding the package, each of its legs then runs as its own ctest over the named suites' `corpus`-labelled tests (never the bare label), its mounts set on that command alone, JUnit to `<package id>.corpus-<leg>.xml`, and a sidecar `<package id>.corpus-<leg>.json` records a named suite that selected nothing (`absent`) and a test registered without `SKIP_REGULAR_EXPRESSION` (`unguarded`); a red leg never fails the create. Under `tools.build:skip_test` it runs nothing; that conf also defines CMake's `BUILD_TESTING` false, from which each package's test and bench switches take their default, so no test target is configured. A test_package's `test()` calls `run_test_package(self)`: the same selection over the test_package's build folder, a second result file `<tested name>/<tested package id>.test_package.xml`, a red failing the create, at least one test owed. Both runners first refuse a test source (under `tests/`, `tests_support/`, or anywhere in a test_package) that spells `__FILE__`, `__builtin_FILE()` or `std::source_location::file_name()`: inside a create malf's path map makes those an identifier, never a path, so a test locates its inputs through a compile definition built from `CMAKE_CURRENT_SOURCE_DIR` (DN-142.D13 (3)); `python3 malf_recipe_tests.py locators <dir>...` prints the same findings for a tree. THE THREE CONF SETS OF A `conan create` are defined in the helper and nowhere else (DN-142.D13 (1), DN-142.D31 (1)), and `create-args <writer|ship|consumer>` prints one: the writer's (`store-create`) sets no skip conf; the ship form's (`store-create --ship`, a candidate's) is `-c tools.build:skip_test=True -c user.malf:run_test_package=True` with the test folder kept, so the package's own tests are neither configured nor run while its test_package is built and run (`run_test_package` reads `user.malf:run_test_package` in place of `skip_test`); the consumer's (the vendor action, the third-party cache producer, any `--build=missing` rebuild) is `-c tools.build:skip_test=True --test-folder=`, which runs no test and builds no test_package on conan's default graph, so it computes the writer's package id. `tools.graph:skip_test` is never set: it prunes the test requirements, and a `test_requires` already present in the graph merges into that node and enters the declaring package's id, so a pruned graph gives metalog, eidos and sift another one. A first-party `test_requires` therefore names a RELEASED package, which every consumer of a published package can resolve. A SKIP IS A RED UNLESS THE PACKAGE DECLARES IT (DN-142.D23). Every judged population, the build tree's and the test_package's, is read row by row from its JUnit: a row whose outcome is `skipped` (a test that printed its `SKIP_REGULAR_EXPRESSION`) or `disabled` (a `DISABLED_` gtest, or `DISABLED` in CMake) fails the run unless the package's `tests/declared_skips.json` holds a row naming that exact test, that outcome and the profile the run was built at. A row is an object with exactly the keys `test` (a full name, never a glob), `outcome` (`skipped` or `disabled`), `profiles` (each one a file in `malf/profiles/`), `condition`, `why` (both non-empty) and `refs`; a malformed row, a row naming a profile malf has no file for, and — on a run with no filter — a row naming a test the run never reported (stale) are DEFECTS and fail the run like an undeclared skip. A declared skip is printed `EXCUSED` and kept in the verdict record's `excused` list, never silently dropped. A test_package skip is never covered by a declaration: a test_package proves the published contract, so it owes every one of its tests. The profile is the create's `user.malf:profile` conf (malf's creates carry `-c user.malf:profile=<profile name>` in the writer's set; a create whose tests ran without it fails, since no skip of it can be judged) and `MALF_PROFILE_NAME` on the desk; a corpus-listed row is not judged here, the corpus legs have their own verdict. `python3 malf_recipe_tests.py judge-skips <junit> <source dir> <profile> <filtered>` prints the same judgment for one result file; `store-create`'s verdict record applies it to each step's results with the declarations read from the step's exported sources (a `conan build` step from its scratch tree, `MALF_STEP_SOURCE`), its verdict failing on an undeclared skip or a defect.

`malf_recipe_exports.py` also carries `export_tracked(self, source, destination)`, called after `narrow_to_tracked`: the files git tracks under a path outside the recipe folder (`../tests_support`) are exported at `destination`, and a source holding none fails the export.

### Conan profile

**The build type is a coordinate of the profile, and there is no verb-level build-type flag.** A profile's `[settings] build_type` is the only declaration of it: it is read at load for the default profile and re-read by `--profile` / `--asan`, and every verb inherits it. `--debug` and `--release` were removed on 2026-09-02 — they were the mechanism by which a build tree came to carry a configuration the profile it is *named* for does not declare, and the tree name is the only thing anyone reads. Measured that day: **all 23** `build-clang21-libcxx-release` trees that a `malf build` / `malf test` had ever configured carried `CMAKE_BUILD_TYPE=Debug`, under a profile declaring `Release`, so the shipped translation units compiled with **no `-DNDEBUG`** and at `SPDLOG_ACTIVE_LEVEL=TRACE` while the directory name said `release`. It bought no compile time either: `-O3` comes from the profile's own `tools.build:cxxflags` whatever the build type. Every `cmake --preset` configure now asserts the tree's `CMAKE_BUILD_TYPE` against the profile file on disk and aborts **before** the compile on a mismatch, so the drift cannot come back silently. Want a Debug leg? Name a profile that declares one: `linux-clang21-libcxx-debug` (the desk debug leg — clang-21 + libc++ at Debug, no sanitizer) or `--asan` (`linux-clang21-asan`, the same build type with AddressSanitizer/UBSan attached).

The dev-default profile `linux-clang21-libcxx-release` (and any `--profile <name>` selection) is resolved from `malf/profiles/` (copied into `$CONAN_HOME/profiles/` on every run so an edit always propagates). Override the default with `MALF_DEFAULT_PROFILE` or the active name with `MALF_PROFILE_NAME`; `malf profiles` lists the registry.

## Self-hosted CI runner (unmetered minutes)

`runner/` provisions an org-level self-hosted runner (label `malf-local`) so the
**private** repos' CI + `release-publish` stop consuming GitHub-hosted minutes. Toggle
hosted⇄local with one org variable (`CI_RUNS_ON=malf-local`). A Windows twin
(`install-runner.ps1`, which registers a Windows **service**; label `malf-windows`) and the
Windows release runner (`coderoast-release-windows`) stand behind one switch:
every private Windows leg runs on GitHub-hosted `windows-2025` by default and on these runners when
the org variable `WINDOWS_RUNNER=self-hosted` (the Founder, 2026-10-08). Public repos stay on the GitHub-hosted runners and
must never target either (fork-PR RCE). Full guide: `runner/README.md`.

## Bundled fallbacks

| File | Purpose |
|---|---|
| `global.conf` | Conan global config (seeded into local cache if missing) |
| `config/.clang-tidy` | Default clang-tidy config (overridden by the project's own `.clang-tidy`) |
| `config/.clang-format` | Default clang-format style (overridden by the project's own `.clang-format`) |
| `config/.clangd` | Default clangd config |

Every C++ repo except `insight-twin` commits these three as **relative symlinks** into
`../malf/config/`. Those resolve in a workspace checkout and **dangle in a standalone
clone** — which is what a CI checkout is. `lint` and `format` both treat a dangling link
as absent and fall back to the path above, so both resolve the same config either way;
neither ever falls through to a tool default (`format` refuses to run rather than let
clang-format silently format to LLVM style).
